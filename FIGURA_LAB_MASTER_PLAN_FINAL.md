1. Executive Summary

Текущее состояние — работающий одностраничный MVP (коммит 821d3c5, index.html 222 строки, style.css 866 строк, script.js 71 строка, два JPEG в assets/). База качественная: дизайн-система в CSS-переменных, семантика без ошибок, prefers-reduced-motion, защита от CLS. Переписывать с нуля не нужно ни при каком сценарии.

До production не хватает не «красоты», а четырёх вещей: честности интерфейса (9 ссылок href="#", вымышленный info@figuralab.ru), доступности (нулевые focus-состояния, нет skip-link, нет focus trap), архитектуры многостраничности (сейчас её нет вообще) и юридического контура (нет политики, согласия, оператора ПДн).

Три решения, которые определяют весь остальной план:





Многостраничность строится на Eleventy (SSG, build-time), а не на ручном копировании header/footer в 11+ файлов. Посетитель получает тот же статический HTML/CSS/JS.



Строгая CSP сохраняется, inline critical CSS не вводится. Конфликт снимается в пользу безопасности.



Backend формы, хостинг и домен не выбираются заранее. Форма проектируется как «готовая к подключению», конкретный endpoint появляется только после ответов Елены и решения по инфраструктуре.

Реалистичная последовательность: Stage 0–1 можно начинать немедленно, они не зависят от Елены. Stage 2 и всё, что дальше, блокируется чек-листом VERIFY_WITH_ELENA. Публикация на боевом домене невозможна до закрытия VERIFY 1, 2, 3, 9, 11, 12 и юридической проверки текстов.



2. Зафиксированные архитектурные решения

Каждое решение окончательное. Вариантов «можно так или так» ниже нет.





Стек посетителя: статический HTML + CSS + один небольшой JS-файл. Никакого клиентского framework runtime.



Генератор: Eleventy (11ty) начиная со Stage 3. До Stage 3 — обычный index.html в корне.



Шапка и футер: один источник — src/_includes/partials/. Ручное дублирование не применяется ни как цель, ни как временный мост.



Журнал: коллекция Markdown-файлов, не рукописный HTML на статью.



Данные сайта (домен, контакты, навигация, счётчики) — в src/_data/*.json, чтобы смена домена или телефона была одной правкой.



CSS: один внешний assets/css/main.css + при необходимости постраничные файлы. Inline critical CSS не вводится.



CSP: style-src 'self', script-src 'self', без unsafe-inline. body.style.overflow заменяется классом body.nav-locked.



Шрифты: self-hosted woff2, subset cyrillic+latin. Google Fonts удаляются полностью.



Email: публикуется открытым текстом в mailto:. JS-обфускация не применяется.



Форма: прогрессивное улучшение. Без backend — рабочие прямые контакты как fallback. Endpoint — одна константа в src/_data/site.json.



Медицинские и специальные категории ПДн через сайт не собираются. Калькулятор считает только в браузере.



JSON-LD без медицинских типов: WebSite, Person, ProfessionalService, BreadcrumbList, Article, FAQPage только там, где FAQ физически есть.



Аналитика: до Stage 10 не подключается вообще. Затем — только Яндекс.Метрика, вместе с cookie-баннером и обновлённой политикой. Google Analytics не используется.



Границы репозитория: marketing site, журнал, калькулятор, frontend формы. Боты, AI-ассистент, личный кабинет, обработка чувствительных данных — отдельные сервисы.



Git: main всегда публикуемый, короткоживущие feature-ветки под крупные фазы, документы плана коммитятся в репозиторий.

Почему Eleventy не нарушает TZ

TZ.md требует: «Использовать чистые HTML, CSS и JavaScript», «Не использовать React на первом этапе», «Не подключать тяжёлые библиотеки». Все три требования относятся к тому, что получает браузер посетителя.

Eleventy работает только на этапе сборки и выдаёт на выходе статические .html-файлы: ноль runtime-JS, ноль гидратации, ноль зависимостей в браузере. Итоговый вес страницы после сборки меньше, чем при ручном дублировании, потому что появляется контроль над общими блоками и версионированием ассетов. Node.js нужен только разработчику и CI.

Формально это расширение TZ, и оно фиксируется здесь как осознанное архитектурное решение: «без React» сохраняется буквально, «без сборки» — снимается, потому что альтернатива (11+ копий шапки и футера плюс растущий журнал) гарантированно приводит к рассинхронизации и делает сайт неподдерживаемым. Это признавал и сам MASTER PLAN v1, предлагая вариант A и тут же описывая его деградацию.

  src["src/ njk + md + data"] --> eleventy["Eleventy build"]
  assets["assets/ css js fonts img"] --> eleventy
  eleventy --> site["_site/ статический HTML"]
  site --> host["Хостинг + security headers"]
  host --> user["Браузер: HTML CSS ~10KB JS"]

Переносится в новую архитектуру без изменений:





Дизайн-система: CSS-переменные палитры, --space-*, радиусы, тени, тайминги (style.css 3–31).



Типографическая пара Cormorant Garamond + DM Sans.

Правило на всю работу сохраняется: палитра, шрифты, тон и общая композиция не меняются. Исключение — точечная правка провальных контрастов (раздел 15).

6. Отклонённые и скорректированные замечания GROK AUDIT





«form-action 'self' может запретить fallback на mailto/мессенджеры» — отклонено как техническая неточность. form-action ограничивает только цель отправки <form>. Обычные ссылки tel:, mailto:, https://t.me/... являются навигацией и под form-action не попадают. Конфликт возник бы только при <form action="mailto:">, которого в плане нет и не будет. form-action 'self' остаётся.



«Cookie-баннер нужен уже сейчас, потому что Google Fonts передают IP» — скорректировано. Google Fonts не ставят cookie; проблема в трансграничной передаче IP, и она решается самохостингом на Stage 0, а не баннером. Вывод MASTER PLAN v1 «баннер не нужен, пока нет аналитики» остаётся верным при условии удаления внешних шрифтов.



«Предпочтительный простой канал для старта — Telegram/MAX webhook вместо serverless» — отклонено в предложенной форме. Отправка в Telegram напрямую из браузера требует токена бота во фронтенде, что недопустимо, а webhook в любом случае означает серверный компонент. Поэтому до появления backend форма не отправляет ничего: работают прямые контакты. Telegram/MAX как канал приёма заявок рассматривается на Stage 9 вместе с выбором хостинга.



«Вариант A (ручное дублирование) оставить как аварийный мост на один спринт» — отклонено. Мост не нужен: между Stage 2 и Stage 3 нет момента, когда требуется вторая страница без генератора. Промежуточное состояние с копиями шапки создало бы работу, которую пришлось бы разбирать.



«rel="noopener noreferrer" на внешние ссылки» — принято частично. noopener подразумевается по умолчанию для target="_blank" в актуальных браузерах, но добавляется явно. noreferrer не добавляется: он ломает атрибуцию переходов и не даёт дополнительной защиты в нашем случае.



«Фильтр медицинского текста на сервере» — принято как отложенное. Пока нет backend, фильтровать негде. На Stage 5 задача решается предупреждением у поля комментария и отсутствием медицинских полей; серверная фильтрация появляется вместе с endpoint на Stage 9.



«Порог: при второй правке шапки или первой статье — Eleventy» — заменено на жёсткое решение. Никаких порогов и триггеров: SSG вводится на Stage 3 безусловно.



«Достаточно 3–4 крупных веток» — скорректировано: одна короткоживущая ветка на стадию, живущая часы или дни и сразу вливаемая в main. Это не «9 долгоживущих веток», а нормальный поток.



7. Финальная информационная архитектура

Двенадцать публичных URL плюс 404. Транслит, слеш на конце, каталог + index.html.

Решения по спорным разделам:





FAQ: отдельной страницы /faq/ не будет. FAQ живёт структурированными блоками на /metod/ (вопросы о подходе) и /programmy/ (вопросы о формате, цене, длительности), плюс сжатый блок из 4 вопросов на главной. Ссылка «Вопросы и ответы» в футере ведёт на /programmy/#faq.



Журнал: в интерфейсе везде «Журнал», URL /zhurnal/. Слово «Блог» из футера уходит.

17. Performance

Целевые значения на mobile: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1. Бюджет страницы: HTML ≤ 50 KB, CSS ≤ 30 KB, JS ≤ 15 KB, изображения первого экрана ≤ 200 KB.

LCP:





Сжатие hero на Stage 0 — не откладывается: 2.81 MB JPEG проваливает LCP с первого дня.



Снять .reveal с hero-контента: opacity: 0 откладывает фиксацию LCP.



preload + fetchpriority="high" на LCP-изображение.



<picture> с современными форматами, srcset 400/520/800/1040, sizes="(max-width: 900px) 90vw, 520px". Сейчас грузится 900px там, где нужно максимум 520px.



Self-hosted шрифты: убирает два внешних соединения и render-blocking. Начертания только используемые — Cormorant 400, 500 и italic 400; DM Sans 400, 500, 600. Cormorant 600 и DM Sans italic из загрузки убираются. Subset cyrillic + latin, font-display: swap, preload двух основных woff2.

CLS:





@font-face с size-adjust, ascent-override, descent-override для fallback — сейчас это основной источник сдвига.



width/height и aspect-ratio на всех изображениях.



Sticky-шапка фиксированной высоты.

INP:





Скролл-обработчик в requestAnimationFrame.



backdrop-filter: blur(12px) уменьшить до 8px, для слабых устройств — непрозрачный fallback через @supports not.



Бесконечная анимация glow-shift (14s) останавливается через IntersectionObserver, когда hero уходит из вьюпорта.

Прочее: минификация при сборке, Brotli/gzip на хостинге, Cache-Control: immutable для версионированных ассетов. Inline critical CSS не вводится — выигрыш при одном CSS-файле маргинальный, а конфликт с CSP реальный.



18. Privacy & Security





HTTPS обязателен, 301 с HTTP, TLS 1.2+. HSTS включается только после стабильной работы сертификата на всех поддоменах.



Заголовки: Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; font-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self', X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=().



Никаких секретов во фронтенде и в репозитории. Сейчас утечек нет — состояние поддерживается.



Google Fonts удаляются: это трансграничная передача IP без основания и render-blocking одновременно.



Специальные категории ПДн (вес, рост, диагнозы, анализы, лекарства, беременность, РПП) через сайт не собираются. Форма принимает имя, контакт, удобное время и общий комментарий с явным предупреждением не указывать медицинские детали.



Калькулятор считает исключительно в браузере, ни один байт не уходит на сервер. Проверяется вкладкой Network.



Валидация формы на сервере (whitelist полей, ограничение длины, проверка формата) появляется вместе с backend. Клиентская валидация — только UX.



Anti-spam: honeypot-поле сразу; rate limiting и капча (Yandex SmartCaptcha или аналог) — при появлении спама, не заранее.



Ошибки наружу обобщённые, без stack trace. ПДн никогда не передаются в URL.



EXIF вычищается из всех публикуемых изображений.



Cookie-баннер не требуется, пока нет аналитики. При подключении Метрики на Stage 10 — баннер, обновление политики и расширение CSP для домена счётчика.



Email публикуется открыто. JS-обфускация не применяется: современные боты её обходят, noscript-fallback снова раскрывает адрес, а UX без JS ломается.
